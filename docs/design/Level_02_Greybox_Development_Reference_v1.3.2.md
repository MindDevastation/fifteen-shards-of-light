## 6.3 `SERIALIZED_BOOTSTRAP_INERT` contract

`SERIALIZED_BOOTSTRAP_INERT` is the canonical authored-state invariant for production `Level_02.tscn` and all mandatory child scenes. It exists before `_ready()`, validator prepare or any runtime mutation.

Minimum serialized baseline:

- Player movement/input is disabled by exact `Level_02.tscn` instance override or a Level-local bootstrap wrapper whose own serialized default is disabled;
- Progress and Arrival are unarmed;
- Trial A statues and Trial B pads/replay input are disabled;
- both shard visuals are hidden, shard `monitoring=false`, shard `monitorable=false`, shard CollisionShape3D is disabled and shard prompts are hidden;
- central/finale presence Areas and return-guidance triggers are disabled;
- SoftReturnVolume cannot recover or mutate Player before commit;
- shared LevelPortal remains its authored `INACTIVE` instance state;
- `ShardRegistrationScope` contains no actual shards and no shared reward callback has been registered;
- environment/finale/portal presentation domains are inert;
- no request, raw collection, admitted collection, trial completion, environment transition, finale event, recovery event or portal event can occur before successful commit.

Prepare only validates these exact serialized properties and builds immutable plans. It must not achieve inertness by calling setters, changing exported values, hiding nodes, disabling Areas or disconnecting signals. The final barrier repeats the full baseline immediately before commit. A pre-commit failure emits one `validation_failed` and requires no rollback because the serialized baseline is unchanged.

Commit may idempotently reassert only the already validated inert state before installing connections and registrations. The final enable order is Progress -> Player controls/process -> Arrival; `validation_passed` is emitted after Arrival is armed. Any gameplay domain active before its assigned step inside the accepted synchronous commit, or any gameplay event emitted before `validation_passed`, is a startup blocker. Progress, Player and Arrival may change armed/enabled state only on their exact assigned commit steps; activation outside commit or earlier than the assigned step is failure, and none of the three may emit a gameplay event until `validation_passed` has been emitted.

# 13. Public API and signal contract

## 13.1 Atomic startup validator

```gdscript
signal validation_passed(run_generation: int)
signal validation_failed(report: Dictionary)

const SERIALIZED_BOOTSTRAP_INERT: StringName = &"SERIALIZED_BOOTSTRAP_INERT"

func validate_and_start() -> void
```

One validation generation produces exactly one outcome. The complete bootstrap has three phases and no rollback phase.

**Phase A - serialized-baseline validation, prepare and immutable plan construction**

- validate every exact `SERIALIZED_BOOTSTRAP_INERT` property before constructing a plan;
- resolve and validate every exact path, node type, object identity, API, signal, exact ID/copy, portal configuration, Environment resource, recovery registry and geometry contract;
- build immutable-after-prepare inert-reassertion, local-connection, shared-registration and per-domain commit plans;
- capture exact emitter, receiver, Callable, shard node and expected serialized/pre-commit identities in the plans;
- do not change visibility, processing/input, monitoring, monitorable, collision, prompt state, signal connections, shared registration, controller state or gameplay arming;
- do not call `Level02ShardSlot.commit_hidden_state()`, any arm/enable method, `Signal.connect()` or shared `register_shard()` during prepare.

**Phase B - final commit-eligibility barrier**

Immediately before commit, without yielding a frame, revalidate that the generation is current, every planned object is alive and identity-equal to the prepared object, every Callable/API remains valid, every planned connection is still absent, shared registration preconditions remain unchanged, every mandatory serialized inert property still matches, all domain plans are complete and no plan was mutated after prepare. Any failure here emits exactly one `validation_failed` and leaves production in its original serialized inert state.

**Phase C - one infallible synchronous commit**

```gdscript
func prepare_start(context: Dictionary, plan_builder: Dictionary) -> bool
func commit_start(prepared_plan: Dictionary, run_generation: int) -> void
```

Commit has no await, deferred mutation, false return, recoverable error branch or failure-to-rollback path. Its exact order is:

1. idempotently reassert the prepared inert state for Player, both shard slots, trials, Areas, recovery, environment, finale and portal-facing local domains;
2. install every exact local signal connection, including request observation, raw collection and admitted collection routing;
3. call current shared `ShardRewardSequenceController.register_shard()` once for each exact actual SoulShard from the prepared registration plan;
4. commit every mandatory domain in the prepared deterministic order while they remain externally unarmed;
5. arm Progress;
6. enable Player controls/process through the validated public/Level-local boundary;
7. arm Arrival last;
8. emit `validation_passed(run_generation)` only after all preceding operations complete.

Progress, Player and Arrival are individually step-locked: only commit step 5 may arm Progress, only step 6 may enable Player controls/process and only step 7 may arm Arrival. A state change outside commit, before its assigned step or repeated through another path is validation failure. Their armed/enabled setters must be event-silent through step 7; no gameplay event may be emitted until step 8 emits `validation_passed`.

The current shared `register_shard()` returns `void` and immediately connects its callback. Compatibility therefore depends on prepare/barrier proving the exact current API, exact shard objects and absence of the shared callback before commit. If any condition can still fail after the barrier, that condition belongs in prepare and the design is not eligible for commit.

## 13.4 RewardGate

`Level02RewardGate` is a **macro-progression admission and release-validity auditor**. It does not own or sequence shared presentation.

Actual `SoulShard.reward_sequence_requested` has two parallel observers:

```text
actual SoulShard.reward_sequence_requested
├── shared ShardRewardSequenceController -> overlay / Player lock / safe completion behavior
└── Level02RewardGate -> macro admission and release-validity audit
```

No callback-order claim is permitted. Shared presentation may begin or safe-complete independently of RewardGate observation. RewardGate cannot stop, delay or precede the shared callback and must never be described as doing so.

Startup authority:

- prepare validates both exact actual SoulShard nodes, current shared `register_shard()` API, exact request signal and exact absence/presence expectations, then creates a registration plan only;
- prepare does not connect RewardGate callbacks and does not call `register_shard()`;
- startup commit installs exact local RewardGate/Slot/Progress connections first, then explicitly calls shared `register_shard()` once per actual shard;
- registration is mandatory and direct; no proxy substitutes for current shared registration.

Runtime authority:

- RewardGate observes actual request node identity, shard ID, exact text, corresponding availability, expected canonical state, collected state and current active admission;
- one canonical request may become the active admitted request;
- duplicate, stale, unexpected, mismatched or concurrent request creates an irreversible reward blocker;
- shared safe completion is not normal-flow proof and does not override the blocker;
- Level02ShardSlot emits `raw_shard_collected(shard_node, shard_id)` for the actual child `SoulShard.collected`;
- only a raw collection matching the active admitted request, exact node identity, ID and still-valid release state may emit `admitted_shard_collected(shard_id)`;
- an unadmitted, stale, duplicate, unexpected or mismatched raw collection never changes Progress or Environment and makes/keeps the run blocked;
- Progress consumes only `admitted_shard_collected`; it has no direct raw Slot/SoulShard collection connection;
- RewardGate never calls `complete_collection_sequence()`, never owns or resets the overlay, never changes Player controls and never fabricates request, collection or success.

The normal-flow concurrency proof remains mandatory: Shard_03 and Shard_04 are spatially separated and shared reward control locking should prevent a second physical request while one sequence is active. If runtime contradicts that expectation, G5 fails; the shared safe-completion path cannot be accepted as a successful canonical order.

## 13.5 Main text

Main-text sequence:

1. Progress reaches FINAL_ACTIVATING and receives actual `final_visual_complete`.
2. It verifies exact main text and calls `LevelFinaleOverlay.show_finale_text(exact_text)`.
3. Player controls are disabled only after the call returns `true`; the controller records ownership of that lock.
4. Only actual `LevelFinaleOverlay.closed` releases the owned lock and requests portal activation once.
5. Missing overlay/API, false return, text-fit/presentation failure or missing close is fail-closed: portal remains dormant, no synthetic close/timer success occurs, owned lock is safely released, and the run is a blocker.
